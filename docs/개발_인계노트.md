계획서 생성도구를 함께 개발하거나 다른 버전(다른 지자체·재난유형·차기 사업)을 만들 때 그대로 가져갈 수 있도록,
**결정한 것과 그 이유**, **겪은 문제와 해결법**, **재사용할 부품**을 모았습니다. 코드 구조는 README, 프로젝트 규칙은 CLAUDE.md를 봅니다.

최종 갱신: 2026-10-05

## 2. 외부 연계 결정

### 2-1. T3Q (대화형 AI 플랫폼)
- 계약 정본: `public/api-docs/t3q.yaml` (Swagger `/api-docs`), 배경 설명: `docs/T3Q_API_요청서.md`, 코드 계약: `src/lib/t3q/types.ts`. **셋을 항상 함께 고친다.**
- 호출은 `src/lib/t3q/client.ts` 한 곳. `T3Q_MODE=mock|live`, live 실패 시 매뉴얼 시드로 자동 대체.
- **API-01 기상요약은 폐지(v1.6).** 기상청 「기상정보」가 이미 (현황)·(전망) 문장으로 오므로 원문을 그대로 쓴다. AI가 공식 원문을 다시 쓰면 공문서 출처가 흐려진다. 번호는 혼선 방지로 유지(API-02 SOP, API-03 인증).
- API-03: T3Q 링크 로그인(`/sso/t3q?token=`), 1회용 토큰 5분, 기관은 행정표준기관코드(부산 6260000, 경북 6470000).
- **필요자원·전파대상·기관**은 별도 API가 아니라 API-02 응답(`resources`, `propagation`, `organizations`)으로 받는다.
- **매뉴얼 고르기(v1.8)**: 상황정보는 T3Q가 벡터DB에서 매뉴얼을 고르는 열쇠. 재난유형 → 발생 시군구 → 시도 → 중앙 순, 그 안에서 대응단계. 위기경보는 **선택** — 지자체 매뉴얼은 대응단계로 나뉘고, 기후부·환경부 실무매뉴얼만 위기경보(관심~심각)로 나뉨(징후감지 = 관심·주의라 1:1 아님). 고른 매뉴얼은 응답 `manual` → SOP 화면 「○○ 기준」.
- **담당부서(v1.9, R19)**: 상황정보에 담당부서(필수 텍스트, 기본 「자연재난과」) → `context.department`. 부산 프로세스 표는 부서 칸으로 행이 나뉨(p.34 초기대응부서=재난상황실·자연재난과, p.35~37 협업부서 약 20개 과, p.38 유관기관). 요청 부서의 행만 받고, 없으면 초기대응 행 + `departmentMatched:false` → 화면 「요청 부서 없음 — 초기대응부서 기준」. **시드(`busan-process.json`)는 p.34만** — 협업부서 행 추출은 남은 일.
- **기상특보 그림 3칸**: 기상특보 현황 · 레이더 영상 · 위성영상(부산 상황보고 양식). 칸 정의는 `WEATHER_SLOTS`(`src/lib/report/weather.ts`) 한 곳. 문서에는 **넣은 그림만** 칸으로 들어가고, 하나도 없으면 3칸 빈 틀. 한글·워드·화면 그림 표는 칸 수를 그림 개수에서 계산.
- **연락망 기본 세팅**: SOP를 만들 때 기관 연락망이 비어 있으면 예시 조직(본부 › 자연재난과·재난안전상황실·OOO과 + **유관기관 5곳**, 홍OO 등 11명, 전파그룹 상황관리반·유관기관)을 자동으로 넣고 「연락망 기본 세팅」 이력을 남김. 상황전파는 유관기관이 가장 중요해 꼭 포함. `src/lib/contacts-seed.ts` `ensureExampleContacts` — 연락망 화면의 빈 안내 「예시 조직 넣기」도 같은 함수.
- **SOP 실행 탭은 순서도가 기본 보기**(목록은 전환).
- **계정·권한(2026-10-05)**: 기본 계정은 운영관리자 1 · 부산 2 · 경북 2 · T3Q 1(`scripts/seed.ts` ACCOUNTS). 계정 발급·비밀번호 지정·권한 변경은 **운영관리자만**(비밀번호 자동 생성 없음). **상황·문서는 모든 계정이 자기가 만든 것만**(운영관리자 포함, `data.ts` ownScope · `canEdit`). `/api-docs`는 운영관리자·T3Q, `/analysis`(분석 그림)·`/admin/*`는 운영관리자만 — `src/proxy.ts` 에서 정적 파일까지 검사. 계정 정리는 `scripts/remove-accounts.ts`(만든 문서가 있으면 지우지 않고 중지).
- **매뉴얼 80종 검증(v2.0)**: 중복 빼고 75종(표준·실무·지자체 현장조치·공공기관·교육시설). SOP 뼈대는 **지자체 현장조치 행동매뉴얼**에서만, 실무·표준은 지자체 행(R24)만 근거로. 규칙은 **일반 규칙 R20~R24 + R25 예외 원칙**(정할 수 없으면 만들지 않고 warnings)으로 묶고, **문서 하나에 맞춘 규칙은 추가하지 않는다**. 결과 페이지: 운영관리자 전용 `/admin/manuals`(데이터 `src/data/manual-analysis.json`, 캡처 `public/analysis/` — 전화번호·성명은 회색으로 가림). T3Q에 공개하는 `/api-docs`에는 두지 않음.
- **연락망 추출 API-04 `POST /contacts`**: 매뉴얼 비상연락망 → 기관·부서·직위·성명·전화·휴대·팩스·분류(AGENCY/INTERNAL/HIGHER/LOCAL_GOV)·기준일·출처. 내부용이라 **성명·휴대전화도 받음**(SOP R17은 유지). 연락망 화면 「매뉴얼에서 가져오기」에서 미리 보고 고른 줄만 `importContacts`(추가·수정만). 규칙 C1~C10.
- **필요시 임무**: `condition`(조치 전체 조건, R8)이 있으면 흐름선 밖 「필요시 임무」 칸에 따로 둠. 다음 임무 자동 선택·완료 집계·상황일지 향후 계획에서 빼고, 실행했을 때만 셈. 제목 일부 조건은 `condition` 아님(R18). `src/lib/sop/kind.ts` `isOnDemand`/`progress`.
- 설명서 `/api-docs/mapping.html`에 **⑤ 우리 화면 적용 · ⑥ 필요시 · ⑦ 다른 프로젝트에 쓸 때(고정/조정)** 추가. 캡처(`public/api-docs/img/app-*.png`)는 로컬 `next dev` + 파이썬 playwright로 찍음(개발 표시 `nextjs-portal` 숨김).

### 2-2. 매뉴얼 → SOP JSON 추출 규칙 (가장 중요한 자산)
- 설명서: `/api-docs/mapping.html` — 매뉴얼 캡처에 번호 상자, 필드 대응, 규칙 R1~R17, 검증한 매뉴얼.
- 계층: **대응단계 → 임무 [n] → 조치 [n-m] (= 행동카드 1장) → 세부행동**. 뼈대는 재난대응 프로세스 표, 기관·전파·자원은 행동카드.
- 원칙: 번호 모양이 아니라 **몇 번째 깊이인지**로 맞춘다. 단계는 이름이 아니라 **열 순서**로 맞춘다.
- 검증 결과
  - 영천 풍수해(행안부 표준 협업기능 코드 ①~⑬): 흐름표 142건 = 행동카드 142장, 가장 잘 맞음 → 경북 다른 시·군도 같은 파서 가능성 높음
  - 기후부 풍수해 실무 / 환경부 산불 실무 / 항만공사 선박사고: 중앙부처·기관 내부용이라 지자체 조치가 거의 없음(R16)
- 매뉴얼 PDF에서 표를 읽을 때는 **글자 좌표로 열·행을 먼저 나눈다**(텍스트 추출 순서는 칸이 섞임). 실명·전화번호는 시드·응답에 넣지 않는다(R17).
- 시드 생성 스크립트 예: 부산 p.34 → `src/data/busan-process.json` (열은 x좌표, 행은 y 범위로 배정).

### 2-3. 기상청 (KMA WthrWrnInfoService)
- `getPwnStatus`로 전국 발효 특보, `getWthrInfo`·`getWthrPwn`은 시도별 지점(stnId)로 조회. **조회 범위는 오늘(KST)만** — 어제 정보가 섞이면 안 된다는 지적.
- 특보 기준 지역은 **상황의 발생 시도**. 현재 위치(헤더)와 다르면 화면에 구분 표시. 발생 시도를 바꾸면 특보를 다시 조회.
- 키는 환경변수 `KMA_SERVICE_KEY`만. 10분 캐시.

## 5. 운영 절차

- 배포: GitHub `jazzsalle/une_report4` main 푸시 → Vercel 자동 배포(icn1).
- DB 스키마 변경: `schema.ts` 수정 → `npm run db:generate`(파일 이름은 의미 있게 바꾸고 `drizzle/meta/_journal.json` tag도 같이) → **배포가 끝난 뒤** 운영에 `DATABASE_URL=… npx tsx scripts/seed.ts`(마이그레이션 포함). 열을 지우는 변경은 새 코드 배포 후 실행해야 옛 코드가 깨지지 않는다.
- 시험 데이터: 운영 DB에서 시험할 때는 시험 전용 id로 만들고 끝나면 지운다. 사용자가 만든 데이터는 건드리지 않는다.
- 비밀정보: `.env*`, `accounts/`, `seed_docs/`는 커밋 금지(공개 저장소). 공식 운영 전 `DEMO_LOGIN` 환경변수 삭제, 계정별 비밀번호 재설정.
- 요금제: Neon 무료는 쉬다가 첫 접속이 느림. 실제 운영 전 Vercel·Neon 요금제 확인.

## 6. 개발 시 주의 (도구·환경)

- Next.js 16: `params`/`cookies`가 비동기, `middleware` 대신 `proxy.ts`, 라우트 타입은 `npx next typegen`. 코드 쓰기 전 `node_modules/next/dist/docs/` 확인.
- 이 저장소는 prettier로 일괄 포맷하지 않는다(파일 전체가 바뀜). 바꾼 줄만 고친다.
- 스크립트로 소스를 고칠 때 템플릿 문자열 안의 정규식 백슬래시가 사라지는 일이 반복됐다 → 정규식 줄은 편집기로 직접 고친다.
- 화면 확인은 로컬 개발 서버 + 크롬에서 직접 눌러 본다(시험 계정은 `docs/테스트계정.md`).
- DB 스키마를 바꾼 뒤에는 개발 서버를 **완전히 껐다 켠다**. PGlite 마이그레이션은 서버가 처음 DB를 열 때만 돈다. `next dev`를 감싼 셸만 끄면 node 프로세스가 포트를 잡고 남으므로 포트 주인 프로세스까지 끈다.
- 저장소 파일은 LF 줄바꿈이다. 윈도 파이썬으로 파일을 쓰면 CRLF로 바뀌어 diff가 파일 전체가 되므로 `newline=''` 또는 편집기를 쓴다.

## 7. 주기적 새로고침 (서버 요청·요금)

- 실행 중 SOP 화면 15초, 분리된 SOP 창·현장 응답 화면 20초마다 서버 값을 다시 받는다. 1회 약 16KB·90ms, 화면 멈칫 없음(측정).
- **화면이 보일 때만** 받고, 탭으로 돌아오면 즉시 1번 받는다 — `src/lib/use-visible-refresh.ts`. 새 화면에서 주기 갱신이 필요하면 `setInterval` 대신 이 훅을 쓴다.
- 부담은 속도보다 무료 요금제 사용량: 화면 100개 × 8시간 ≈ 하루 19만 요청(숨은 탭 제외 전).
